## 1. Product ruling

Hornelore stores a photograph once. A trip may include that photograph once, and the operator may place that trip photograph on zero, one, or several trip days. A day may contain any number of photographs.

The normal action is **Add to this day**. Adding a second day does not remove the first placement. **Move here** is a separate, explicit compound action: add the destination placement and remove the chosen source placement in one transaction. **Remove from this day** removes only that placement. None of these actions deletes the trip membership, the photo row, the original file, or shared derivatives.

There is no product hard cap on photos per day. The UI must remain usable through progressive batches and thumbnail rendering rather than enforcing an arbitrary data limit.

This is a dated reversal of Travel Document Doctrine ruling 1.12. The old ruling correctly warned that "Also show on another day" required a schema change. This work order authorizes that schema change; it must not be implemented as a button over the old scalar column.

## 2. Why this model

The mature-library pattern is asset → collection membership → placement:

- Google Photos permits a media item in multiple albums, caps an album at 20,000 items, and batches additions in groups of at most 50.
- Apple Photos removes an item from an album without removing it from the library or other albums.
- Immich permits assets in multiple albums and generates shared thumbnail/preview derivatives from one original.
- PhotoPrism serves thumbnails/previews for browsing instead of repeatedly loading originals.

Hornelore already has the correct physical half of this design:

- one original at `DATA_DIR/memory/archive/photos/{narrator_id}/{photo_id}/original.ext`;
- one shared `thumb_400.jpg` derivative generated by `services/photo_intake/storage.py`;
- thumbnails served by `/api/photos/{photo_id}/thumb`.

This WO changes logical placement. It does **not** duplicate originals or create a separate photo row per day.

Reference material:

- Google Photos album management: <https://developers.google.com/photos/library/guides/manage-albums>
- Apple Photos album behavior: <https://support.apple.com/guide/photos/add-remove-and-rearrange-photos-in-albums-pht6d60a1f1/mac>
- Immich albums: <https://immich.app/docs/features/albums>
- Immich thumbnail generation: <https://immich.app/docs/administration/jobs-workers>
- PhotoPrism thumbnails: <https://docs.photoprism.app/developer-guide/media/thumbnails/>

## 3. Current state and defects

### 3.1 The scalar placement restriction

`trip_photo_links` represents trip membership and is correctly unique on `(trip_id, photo_id)`, but it also carries one nullable `trip_day_id`. The UI therefore describes an already placed photo as "Move to this day," and `photo_links_set_day()` overwrites the prior day.

One day can already hold multiple different photo links. The missing capability is one trip photo on multiple days.

### 3.2 Misleading day-card counts

`trip_day_counts()` currently adds two values into `photos`:

1. links explicitly attached through `trip_day_id`; and
2. otherwise-unattached links whose taken date matches the day.

That is why a day can display two photos even when fewer are actually placed there. Date matches are useful suggestions, but they are not operator placements and must not be presented as the day's attached-photo count.

### 3.3 Blocking deletion hazard

`_day_attachment_counts()` feeds `_day_is_empty()`, `trip_days_reconcile_preview()`, and the transactional `drop_empty_out_of_range` path. Today it counts photo attachments from `trip_photo_links.trip_day_id`.

If the new placement table lands without changing this query in the same phase, a day containing only new-style photo placements will report zero attachments. Shrinking a trip's date range could then silently delete that day. Preventing this is the first blocking acceptance gate, not cleanup.

### 3.4 Acceptance harness encodes the old model

`scripts/wo02_acceptance.py` snapshots each link as `{"day": scalar}` and verifies return to one original day. Under many-to-many that assertion is false. The harness must store a normalized `days: [...]` set and prove that removing one placement leaves every other placement, the trip link, and the photo intact.

Current-main clarification (commits `10c44f8`, `5d1a4fa`, and `e6388ae`, reviewed 2026-08-12): WO-02 now correctly implements all four required modes—`capture`, `checkpoint`, `verify`, and `restore-verify`—plus separately labelled operator attestations for the dirty guard and modal reopen. Commit `e6388ae` corrected `verify --attest` so it persists and reports the attestation before `_verdict()` without inflating PASS. This WO does **not** replace or redesign that accepted four-stage instrument. It changes only the photo-placement shape and the assertions that currently assume one scalar day. Preserve the PASS/FAIL/INCOMPLETE/ATTEST distinctions, transcript identity checks, checkpoint baseline, main-dispatch coverage, output-order/count coverage, restart proof, and restoration proof.

## 4. Canonical data model

Add migration `0043_trip_photo_day_placements.sql` (or the next unused migration number at execution time):

```sql
CREATE TABLE trip_photo_day_placements (
    id TEXT PRIMARY KEY,
    photo_link_id TEXT NOT NULL,
    trip_day_id TEXT NOT NULL,
    placement_note TEXT,
    ord INTEGER NOT NULL DEFAULT 0,
    placement_method TEXT NOT NULL DEFAULT 'operator',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY(photo_link_id) REFERENCES trip_photo_links(id) ON DELETE CASCADE,
    FOREIGN KEY(trip_day_id) REFERENCES trip_days(id) ON DELETE CASCADE,
    UNIQUE(photo_link_id, trip_day_id)
);

CREATE INDEX idx_trip_photo_day_placements_day_ord
    ON trip_photo_day_placements(trip_day_id, ord, id);
CREATE INDEX idx_trip_photo_day_placements_link
    ON trip_photo_day_placements(photo_link_id);
```

Migration requirements:

- Backfill one placement for every live `trip_photo_links.trip_day_id`.
- Preserve the link id, photo id, trip id, caption, approval, context, hidden state, assignment metadata, and file paths unchanged.
- Make rerunning migration discovery safe according to the repo's existing migration runner conventions.
- Do not drop or null the legacy column in this WO's first migration.
- The migration test must prove exact backfill counts and uniqueness.
- The migration must reject or surface cross-trip corruption; it must not quietly create a placement whose day's `trip_id` differs from its link's `trip_id`. SQLite cannot express that rule with the two simple foreign keys, so repository writes must validate it transactionally.

### 4.1 Metadata ownership

| Scope | Fields |
|---|---|
| Permanent photo asset (`photos`) | original, derivatives, archive identity, file hash, intrinsic capture metadata |
| Trip membership (`trip_photo_links`) | trip, shared caption, Lori approval, shared operator context, memoir inclusion, hidden state, assignment/provenance |
| Day placement (`trip_photo_day_placements`) | day, ordering, optional day-specific `placement_note`, placement method, timestamps |

Caption and Lori approval remain shared. A different day may need a short placement note, but it does not get a second truth-changing caption in this phase.

## 5. Authority and transition rule

The new table becomes authoritative for day placement after backfill. `trip_photo_links.trip_day_id` remains physically present only as a compatibility bridge while all known readers are migrated.

Rules:

1. New placement APIs write to `trip_photo_day_placements` only. During Phase 1 only, the still-live legacy `photo_links_set_day()` path is a narrowly scoped compatibility bridge: it must dual-write the legacy scalar and the corresponding placement change in one transaction. Phase 2 removes that legacy-column write when the UI/API switch lands. No non-bridge code may introduce another legacy write.
2. No new code may treat the legacy column as a second source of truth.
3. Compatibility serialization may emit a scalar `trip_day_id` only when exactly one placement exists; it must also emit authoritative `trip_day_ids` and/or `day_placements`.
4. Zero placements serializes scalar `trip_day_id` as null. More than one placement must not choose an arbitrary scalar day; serialize scalar null and the complete collection.
5. Existing consumers must be migrated deliberately. Audit at least `chat_ws`, `trip_placement`, `trip_story_capture`, `travel_doc_lori_modal`, `import_provenance`, the trips router, `trip_repository`, both Travel Document frontends, memoir/timeline projections, and tests/fixtures. Use `rg` to find the full set; this list is not permission to stop searching.
6. Dropping `trip_photo_links.trip_day_id` is a later migration after live acceptance and a fresh consumer audit. It is not part of the additive first commit.

## 6. API contract

Keep the existing day-scoped route family, but change it from scalar mutation to placement operations. Exact response names may follow repo conventions, but the semantics are binding.

### 6.1 Add placements

`POST /api/trips/{trip_id}/days/{day_id}/photos/link`

- Accept existing `photo_link_ids` and current `photo_ids` promotion path.
- Create missing trip membership, if authorized, and day placement in one repository transaction.
- Idempotent for an already-existing `(photo_link_id, trip_day_id)` pair: return success and identify it as already present; never duplicate it.
- Validate narrator ownership, trip ownership, day ownership, hidden/deleted posture, and cross-trip mismatch before writes.
- Batch maximum: 50 requested items per call. This is a transport/UI batching limit, not a per-day data cap.
- A request containing 51 or more items is rejected in full with HTTP 400. Never truncate silently and never partially apply the first 50.
- Add-many assigns increasing `ord` values after the day's current maximum, in request order. It must not leave every new row at the default `0` and rely on the id tie-breaker for visible order.
- A concurrent duplicate that loses the `UNIQUE(photo_link_id, trip_day_id)` race is classified by that constraint and returned as an idempotent/already-present result or a named 409—not an unclassified 500. Follow the S2 `IntegrityError` handling pattern.

### 6.2 Remove placements

`POST /api/trips/{trip_id}/days/{day_id}/photos/unlink`

- Delete only the named placement rows for that exact day.
- Preserve other placements, trip membership, photo row, original, thumbnail, caption, approval, and shared context.
- Idempotent or explicit not-present result; never fall back to deleting the link.

### 6.3 Move one placement

Add a dedicated move operation accepting `photo_link_id`, `from_day_id`, and `to_day_id`.

- One transaction: validate both days and link, add destination, remove source.
- If the destination already exists, removal of the named source may still complete, with an explicit response.
- A failed destination add leaves the source placement intact.
- "Move" must name its source. A photo on three days cannot be moved correctly from a bare link id alone.

### 6.4 Read models

Photo-link inventory responses must include:

- `day_placements`: stable ordered objects including placement id, day id, `ord`, method, and optional placement note;
- `trip_day_ids`: normalized stable list for lightweight consumers;
- compatibility `trip_day_id` under the transition rule above.

Day timeline responses include the placement id as well as the shared photo-link id. This lets the UI remove or reorder one occurrence without ambiguity.

### 6.5 Timeline and document export rulings

`trip_timeline_projection` classifies a trip photo under **Needs a day** only when the link has **zero placements**. A photo with one or several placements must not also appear as unplaced merely because the compatibility scalar is null.

The primary UI now centralizes the same question in `travel-doc-lab.js::linkIsUnplaced()` (`5d1a4fa`). Migrate that helper in Phase 2/3 to authoritative set semantics: unplaced means no stop **and zero day placements**. It must use `trip_day_ids`/`day_placements`, not the compatibility scalar. The filter count, filtered gallery, and lightbox location label must continue sharing one definition. Add a regression case where scalar `trip_day_id` is null because a link has two placements; the UI must not call it unplaced.

The Travel Document DOCX renders a multi-day photo once under **each day on which the operator explicitly placed it**. This deliberately changes the prior closeout observation that four photos happened to embed exactly once; that was a consequence of one-day data, not an enforced export invariant. The original asset and thumbnail remain single stored files even when the document embeds the photo in several day sections. Export ordering follows each placement's `ord`. A photo with zero placements follows the existing unplaced/export policy and must not be assigned to a day by taken-date inference.

Phase 2 must add projection and DOCX tests for zero, one, and several placements, including: a Day 1 + Day 3 photo appears once in each of those two sections, nowhere else, and never in **Needs a day**; one-day photos retain current output; shared captions remain consistent.

## 7. Counting and suggestion semantics

The day card's main `photo_count` means **explicit, live, visible placements on that day**.

- Same photo placed on Day 1 and Day 3 counts once on each day.
- Same link cannot count twice on one day because of the unique constraint.
- Hidden trip links do not appear in display counts or timelines, but their placements still count as attachments for deletion safety.
- Soft-deleted photos do not appear in display counts.
- Trip inventory's unique-photo count counts the trip link once regardless of placement count.

Date matching becomes a separate suggestion value, for example `photo_suggestion_count`, and a separate picker section such as "Taken on this date." It must exclude photos already placed on that day. It must never be added into `photo_count`.

Operational failures in either placement counts or suggestion counts must surface through the existing warning/classified-SQLite posture. Do not translate locks, I/O failures, missing tables, or malformed queries into zero.

## 8. UI requirements

The Travel Document day inspector needs two clear surfaces:

1. **On this day** — explicit placements, ordered, with Remove from this day and optional Move here/from controls.
2. **Photo library / suggestions** — unique trip photos and narrator archive candidates, with Add to this day. A photo already on other days shows those day labels and remains addable here.

Behavior:

- Add is the primary action. Move is separate and deliberate.
- A day accepts many photos.
- The same photo may be on multiple days.
- Removing the last placement leaves it in the trip inventory.
- Show a 400px thumbnail in grids; open the original only for deliberate full view/download.
- Load 50 items initially and 50 per explicit "Load more" or scroll batch.
- Do not apply a hard per-day cap. Add a non-blocking performance warning only if evidence supports it (initial threshold 500 placements is acceptable).
- Keep the DOM bounded/virtualized when a day or library grows beyond roughly 200 visible items.

### 8.1 Nested-scroll thumbnail hazard

The day inspector/picker has its own `overflow:auto` scroll container. Native `loading="lazy"` previously evaluated against the wrong scrollport and left images unloaded. Do not reintroduce that failure.

Use either eager loading for each bounded 50-item batch or an `IntersectionObserver` whose `root` is the actual picker scroll container. Keep `thumbImg(photoId, alt, lazy)` as the deliberate decision point and test the generated markup/observer wiring structurally and behaviorally.

### 8.2 Both frontends

`travel-doc-lab.js` is the primary product surface. The retired-but-served `travel-documenter.js` remains a testbed after U7. Either port this feature to both surfaces in the same UI phase or make the legacy page explicitly read-only for photo placement. Do not leave a reachable old page writing the legacy scalar authority.

## 9. Blocking safety properties

These tests land before or with the first production reader switch:

1. A day whose only content is one new-table photo placement is **not empty**.
2. Shrinking trip dates with `drop_empty_out_of_range=true` refuses to delete that placement-only day and reports `holds.photos >= 1`.
3. A hidden photo link's placement still protects the day from deletion.
4. A soft-deleted photo/link posture follows the existing attachment-preservation rule and cannot license silent day deletion.
5. A locked or failed placement-count query raises/surfaces an error; it never returns zero and licenses deletion.
6. Deleting/removing one placement leaves all other placements, the trip link, photo row, original, and thumbnail intact.
7. Deleting the trip link cascades its placements only; deleting a trip/day follows existing explicit cascade policy and is covered with exact row assertions.
8. Cross-trip and cross-narrator placement attempts perform zero writes.
9. Concurrent duplicate adds yield one placement and a clean success/conflict result, not a 500.
10. Add/move operations are transactional; injected failure proves no half-move and no orphan membership.
11. During the Phase 1 compatibility window, a placement made through legacy `photo_links_set_day()` creates/updates the placement row in the same transaction; the placement-only attachment tally then prevents deletion of that day. An injected failure rolls both representations back.

Tests must assert rows and observable behavior, not merely source-token counts. Mutation/non-vacuity checks are required for the deletion guard, remove-one-preserves-others, cross-trip rejection, and exact UIs' add-vs-move behavior.

## 11. Performance acceptance

- Repository/API test with at least 1,000 placements on one day; no schema or product cap.
- Requests add at most 50 at a time.

## 14. Definition of done

This WO is done only when:

- a single permanent photo can be explicitly placed on multiple trip days;
- a day can hold many photos without an arbitrary cap;
- Add, Move, and Remove from this day have distinct, correct semantics;
- one placement can be removed without disturbing another placement or the asset;
- day counts report explicit placements and date matches are separate suggestions;
- thumbnails—not originals—power scalable grids;
- the date-shrink deletion path treats placement-only days as non-empty and fails closed on query errors;
- all server/frontend consumers use the new authoritative model;
- the revised WO-02 harness certifies set semantics across restart and restoration;
